# SnpLinAlg SIMD kernels on x86 AVX-512

The kernels in `src/linalg_simd.jl` were developed on an Apple M1, and eight
of its docstrings marked their tuning constants as "heuristic default
awaiting one benchmark run on an AVX2/AVX-512 x86 machine". This is that
run.

## Environment

| Fact | Value |
| --- | --- |
| CPU | Intel Xeon 6736P (`Sys.CPU_NAME = graniterapids`) |
| ISA | `avx512f dq bw vl vbmi vnni fp16`, `amx_tile`, `avx_vnni` |
| Topology | 72 cores, 2 sockets x 36, 1 thread per core |
| Cache | L1d 48 KiB/core, L2 2 MiB/core, L3 144 MiB/socket |
| Allocation | 12 cores pinned to 36-47 (one NUMA node), 32 GB |
| Julia | 1.12.7 |
| `VECTOR_BYTES[]` | 64 (auto-detected) |
| `_micro_tile` | `(8, 32)` for `Float32`, `(8, 16)` for `Float64` |
| Benchmark shape | `EUR_subset` stacked 20x: m = 7580 samples, n = 54051 SNPs |

`_micro_tile` returning `MR = 8` and `W = 16` means every register-tiled
code path measured here had never executed before; the M1 always took the
`(6, 16)` / `(6, 8)` branch.

## Summary

1. **`transpose(A) * X` runs at half speed because `mul!` wraps the packed
   genotypes in a `SubArray`.** Passing the dense `Matrix{UInt8}` instead is
   1.77x to 2.04x faster for every `k >= 8` and both element types. This is
   the one actionable defect found.
2. `VECTOR_BYTES = 64` is correct on this host. LLVM emits `zmm` registers
   and spills nothing from the hot loop, and once finding 1 is accounted
   for, the 512-bit tile wins at every `k` tested.
3. **The five budget constants need no change.** Across 106 swept tile
   configurations the current `_tile_sizes` defaults were within 1.15x of the
   best configuration in all eight operation/type cells.
4. Correctness on the previously unexecuted AVX-512 tiles is clean: 10046
   tests pass at 1, 2, and 12 threads.
5. **Against registered `SnpArrays v0.3.23` this fork won 14 of 16
   operation/type/k cells**, by 1.11x to 2.84x, with matching results to
   1e-14. Both losses were `Float32` at k = 8.
6. Two cheap changes following from 1 and 2 (see "After tuning") take
   `transpose(A)*X` up by 1.6x to 2.0x and leave **all 16 cells favouring
   this fork**.

## Generated code

`code_native(..., syntax = :intel)` on `_snparray_AX_micro_tile!` and
`_snparray_AtX_micro_tile!`, counting inside the hot column loop (between
the loop header and its backedge):

| Variant | Vector regs | FMAs in loop | Spills in loop |
| --- | --- | --- | --- |
| `AX`, `Float32`, vb64 | `zmm` | 16 `vfmadd231ps` | 0 |
| `AX`, `Float64`, vb64 | `zmm` | 16 `vfmadd231pd` | 0 |
| `AtX`, `Float32`, vb64 | `zmm` | 16 `vfmadd231ps` | 0 |
| `AtX`, `Float64`, vb64 | `zmm` | 16 `vfmadd231pd` | 0 |
| `AX`/`AtX`, vb32 | `ymm` | 12 | 0 |

Two questions raised in the source docstrings are answered:

- LLVM's `prefer-vector-width` default did **not** split the 512-bit
  vectors. The remedy suggested at `VECTOR_BYTES` (falling back to 32) is
  not needed on graniterapids with Julia 1.12.
- `MR = 8` with `U = 2` needs 16 accumulators + 2 rhs + 1 broadcast = 19 of
  32 `zmm`, and the register allocator confirms it: zero spills in the loop.
  The stack traffic that a naive grep finds (24 to 68 instructions) is
  entirely the prologue zeroing and the lane-extraction epilogue, which
  stores each accumulator once per tile in order to index `vector[lane]`.

## Finding 1: the `SubArray` wrapper in the transpose `mul!`

The forward `mul!` passes the genotype array straight through
(`linalg_direct.jl:104`, `:120`):

```julia
_snparray_AX_tile!(out, sla.s.data, rhs, sla.values, sla.s.m)
```

The transpose `mul!` instead delegates to the `cols` method
(`linalg_direct.jl:141`, `:175`), which wraps both arrays in views even when
`cols` is the full `1:size(sla, 2)` (`:162-163`, `:196-197`):

```julia
packed = view(sla.s.data, :, cols)
values = view(sla.values, :, cols)
```

`_snparray_AtX_kernel!` accepts `StridedMatrix`, so this compiles and is
correct, but it specializes the kernel on
`SubArray{UInt8, 2, Matrix{UInt8}, Tuple{Slice{OneTo{Int64}}, UnitRange{Int64}}, true}`
rather than `Matrix{UInt8}`. Timing the same driver on both, same process,
same data:

| | dense | view | ratio |
| --- | --- | --- | --- |
| `Float32` `Aᵀ*y` k = 1 | 5.016 ms | 4.913 ms | 0.98x |
| `Float32` `Aᵀ*Y` k = 8 | 17.597 ms | 33.619 ms | **1.91x** |
| `Float32` `Aᵀ*Y` k = 32 | 21.720 ms | 38.801 ms | **1.79x** |
| `Float32` `Aᵀ*Y` k = 128 | 83.651 ms | 147.795 ms | **1.77x** |
| `Float64` `Aᵀ*y` k = 1 | 7.165 ms | 6.662 ms | 0.93x |
| `Float64` `Aᵀ*Y` k = 8 | 16.383 ms | 33.403 ms | **2.04x** |
| `Float64` `Aᵀ*Y` k = 32 | 39.840 ms | 74.696 ms | **1.87x** |
| `Float64` `Aᵀ*Y` k = 128 | 159.233 ms | 283.020 ms | **1.78x** |

The measured `mul!` time tracks the `view` column to within 5% in every row,
confirming the view is the whole difference. In GFMA/s, `Float32` `Aᵀ*Y`
k = 128 goes from 354.8 to 626.9.

Only the register-tiled `AtX` kernel pays this; the `k = 1` vector kernel
`_snparray_atx_kernel!` is unaffected. The likely reason is
`_load_packed_bytes` (`linalg_simd.jl:641-650`), which issues `MR = 8`
scalar loads `packed[byte_index, column + c - 1]` per four samples — cheap
index arithmetic on a `Matrix`, the reindexing path on a `SubArray`.

The forward kernels never pay it, which is why `A*X` shows no such gap.

## Finding 2: `VECTOR_BYTES`

Crossing the packed-array type with `VECTOR_BYTES[]` on `Aᵀ*X` separates the
two effects:

| | vb64 view | vb32 view | vb64 dense | vb32 dense |
| --- | --- | --- | --- | --- |
| `Float32` k = 8 | 33.4 ms | 16.5 ms | 16.4 ms | 15.3 ms |
| `Float32` k = 32 | 38.4 ms | 41.7 ms | **21.7 ms** | 37.9 ms |
| `Float32` k = 128 | 147.9 ms | 161.1 ms | **84.0 ms** | 148.2 ms |
| `Float64` k = 8 | 34.2 ms | 21.3 ms | **14.7 ms** | 18.6 ms |
| `Float64` k = 32 | 75.1 ms | 78.2 ms | **40.5 ms** | 77.6 ms |
| `Float64` k = 128 | 281.7 ms | 309.9 ms | **157.2 ms** | 284.6 ms |

Read only the `view` columns and `VECTOR_BYTES = 32` appears to win at
k = 8 by up to 2x, which would suggest that `NR = 32` wastes lanes on a
narrow rhs. It does not: on the dense path `VECTOR_BYTES = 64` wins by
1.27x to 1.92x everywhere except `Float32` k = 8, where the two tie within
7%. The apparent k = 8 regression was the `SubArray` penalty interacting
with tile shape, not lane waste.

**Recommendation: keep `VECTOR_BYTES = 64` on AVX-512.** The docstring's
`prefer-vector-width` caveat and the "heuristic default awaiting one
benchmark run" note can both be replaced with this measurement.

## Finding 3: the tile-size budgets

`benchmark/tile_sweep.jl` re-implements the four schedulers from
`linalg_direct.jl:202-294` with `row_step`, `column_step` and `rhs_step` as
arguments, so the derived tile sizes can be swept without rebinding the
`const` budgets. Each driver is checked against `mul!` before any timing.

106 configurations at m = 7580, n = 54051, 12 threads, minimum of 3 runs:

| Sweep | Operation | Default triple | Best triple | Speedup |
| --- | --- | --- | --- | --- |
| S2 | `Float32` `A*x` | (256, 54051, 1) | (1024, 54051, 1) | 1.13x |
| S2 | `Float64` `A*x` | (256, 54051, 1) | (256, 54051, 1) | 1.00x |
| S3 | `Float32` `A*X` k=32 | (256, 512, 32) | (256, 2048, 32) | 1.01x |
| S3 | `Float64` `A*X` k=32 | (256, 256, 32) | (256, 256, 32) | 1.01x |
| S4 | `Float32` `Aᵀ*x` | (4096, 1136, 1) | (4096, 512, 1) | 1.15x |
| S4 | `Float64` `Aᵀ*x` | (2048, 1136, 1) | (16384, 1136, 1) | 1.09x |
| S5 | `Float32` `Aᵀ*X` k=32 | (2048, 1136, 32) | (1024, 1136, 32) | 1.06x |
| S5 | `Float64` `Aᵀ*X` k=32 | (2048, 1136, 32) | (2048, 1136, 32) | 1.01x |

No cell yields more than 1.15x, so none of the five budgets warrants a
change on this host. Shape of the response surface:

- `row_step` for `A*x` and `A*X` is sharply peaked at the low end. 256 is
  best or within 1% of best; 8192 costs 4.8x on `A*x` and 4096 costs 4.4x on
  `A*X`. `TASK_AXIS_FLOOR = 256` is landing exactly on the optimum.
- `column_step` for `A*X` is flat from 256 upward (58.5 to 60.2 ms across
  256-2048 for `Float32`) and only degrades at 128. The current 512 sits on
  the plateau.
- `Aᵀ*x` prefers a *smaller* `column_step` (512 beats 1136 by 1.15x for
  `Float32`) and a larger `row_step`.
- `Aᵀ*X` prefers the smallest `column_step` tested (1136) with `row_step`
  1024-2048. Larger `row_step` raises panel allocation steeply: (8192, 1136)
  allocates 48 MB per call for a slower result than (1024, 1136) at 6 MB.

The pre-measurement expectation that `L2_PANEL_BUDGET = 256 KiB` would be
8x too small for a 2 MiB private L2 was **not** borne out. Enlarging the
panel past the current derivation is neutral at best and, on the `Aᵀ*X`
`row_step` axis, actively worse.

the same constructor and all four `mul!` methods, so every operation has a

## After tuning

Two changes were applied on the strength of the findings above. The five
budget constants were left alone.

**A. The transpose `mul!` no longer wraps in views.** The two no-`cols`
methods in `linalg_direct.jl` are now self-contained and pass `sla.s.data`
and `sla.values` straight to the tile driver, as the forward pair always
did. The `cols` methods are unchanged.

**B. The rhs lane count is chosen from k.** `_rhs_width(T, k)` returns the
largest power of two at most `_vector_width(T)` and not exceeding `k`,
floored at 4; both matrix drivers use it in place of `_vector_width(T)`, and
the panel buffers are sized from the width actually in use rather than from
`_micro_tile`.

Isolated effect of B at k = 8, `Float32`, dense packed, interleaved samples:

| | W = 16 | W = 8 |
| --- | --- | --- |
| `A*X` min / p25 / median | 50.0 / 51.2 / 51.7 ms | 48.7 / 51.2 / 52.1 ms |
| `Aᵀ*X` min / median | 17.4 / 22.6 ms | 16.9 / 17.2 ms |

B is a wash for the forward kernel — the p25 values are identical to three
decimals — and worth 1.31x on the median for the transpose kernel. It also
halves the panel allocation wherever the width narrows: `Aᵀ*Y` at k = 8
`Float32` fell from 12.63 MB to 6.32 MB per call. `Float64` on AVX-512 is
unaffected, since `_vector_width` is already 8 there.

B was kept despite the forward result being flat, because it is not merely
an extra specialization: it carries a measured transpose win and the
allocation reduction.

Applying change A to the `k = 1` vector method was consistency rather than a
measured win. Interleaved re-measurement confirms it is neutral: dense vs
view differs by at most 3% with mixed sign in both element types.

Correctness after both changes: 10458 tests pass (10046 previously plus 412
new `_rhs_width` invariant tests), 0 failing, at 1, 2 and 12 threads and
with `VECTOR_BYTES[] = 32`. The scalar-fallback relative errors are
unchanged to every printed digit.

## Panel workspace and the restricted-column path

Two further changes, following from the allocation figures above and from
where `SnpVarianceComponents` actually calls in.

**C. The packing panel lives on the `SnpLinAlg`.** A `panel::Vector{T}`
field replaces the `zeros(T, ...)` that each task ran on entry. Both matrix
drivers size it to `tasks * panel_length` and hand each spawned task the
slice at its own `panel_offset`, so tasks still never overlap. It is resized
to an exact fit, so a repeated product at one shape reuses the buffer and a
change of shape reallocates. The field is not reentrant: concurrent `mul!`
calls on one operator would share it. Nothing in this repository does that —
the only `Threads.@spawn` outside the SnpArrays kernels is the Rademacher
worker pool, which runs its own kernel.

**D. The `cols` methods index dense arrays.** They previously built
`view(sla.s.data, :, cols)` unconditionally. An `out_offset` now travels
through the `atx`/`AtX` chain, so `column_first`/`column_last` index the full
genotype arrays while `out` is written at `column - out_offset`. The
no-`cols` methods delegate to them again, which removes the duplication that
change A had introduced.

This matters because both CPU-backend entry points pass an explicit range:
`block_probe_product!` (`src/backend_cpu.jl:107`) and `block_dense_product!`
(`:125`), over blocks of `min(n, 4096)` columns (`src/accumulate.jl:117`).
Change A alone never reached them.

| `Float64` `A*X` k=128 | 999936 B | 16016 B | 62x |

What remains is the `Threads.@spawn` task overhead, about 425 B per task,
which the `k = 1` vector kernels already paid and which no workspace can
remove. The vector kernels are unchanged at 12.8 KB and 21.2 KB.

Sharing one buffer costs no throughput. Interleaved samples, 15 repeats:

| | shared min / median | per-task min / median |
| --- | --- | --- |
| `Float32` `Aᵀ*X` k=32 | 24.527 / 27.271 ms | 25.076 / 29.792 ms |
| `Float32` `Aᵀ*X` k=128 | 99.804 / 109.709 ms | 106.091 / 109.414 ms |
| `Float64` `Aᵀ*X` k=32 | 49.180 / 51.381 ms | 49.720 / 53.713 ms |
| `Float64` `Aᵀ*X` k=128 | 192.677 / 204.130 ms | 195.657 / 203.067 ms |

The shared buffer is ahead on the minimum in all four cells and within 1-2%
on the median. Slice boundaries are multiples of 64 bytes, so there is no
false sharing between tasks.

### The restricted-column path

4096-column blocks, the width `SnpVarianceComponents` uses. Dense indexing
against the previous view-building behaviour, same process, results checked
equal:

| | view | dense | gain |
| --- | --- | --- | --- |
| `Float32` k=32 | 4.712 ms | 3.086 ms | 1.53x |
| `Float32` k=128 | 20.233 ms | 14.748 ms | 1.37x |
| `Float64` k=32 | 8.934 ms | 5.915 ms | 1.51x |
| `Float64` k=128 | 37.303 ms | 26.399 ms | 1.41x |

1.32x to 1.53x across the blocks and widths tested — less than the 1.77x to
2.04x measured at the full 54051 columns, since a 4096-column block is a
smaller working set with a different tile shape.

### Test coverage

The CPU `cols` methods had **no test coverage at all** before this change;
the only `cols` test in the repository is `test/metal_vc.jl`, which is
Metal-only and does not run on x86. `out_offset` is zero unless the range is
restricted, so the entire change would have been untested. A new testset
covers 12 ranges (single columns, ranges crossing tile boundaries, lengths
that are and are not multiples of `MR`) across `Float32`, `Float64` and the
`Float16` scalar fallback, transpose and adjoint, at k = 1, 8 and 33, plus
agreement between a restricted block and the corresponding rows of the full
product, and the four validation errors.

Totals: 11050 tests pass at 1, 2 and 12 threads and with
`VECTOR_BYTES[] = 32`. The full SnpArrays suite, the SnpRademacher suite, and
the non-Metal `SnpVarianceComponents` tests (`reference`, `groups`,
`projection`, `accumulate`, `mom`) all pass.

### A caveat on absolute timings

Seven other jobs were scheduled onto n1183 during this part of the session.
Our 12 cores stay pinned to 36-47, but the socket's L3 and memory bandwidth
are shared, and absolute timings drifted upward by roughly 20% against the
earlier tables. Every comparison in this section is interleaved or
same-process for that reason; the cross-run tables above it were taken on a
quieter node and should not be compared directly against these.

## The tile-budget constants

| Constant | Current | Recommended | Basis |
| --- | --- | --- | --- |
| `VECTOR_BYTES` | auto (64 here) | unchanged | `zmm` emitted, no hot-loop spills, 1.27-1.92x over 32 on the dense path |
| `L1_OUT_BUDGET` | 16 KiB | unchanged | S2/S4; best alternative 1.13x on one of four cells |
| `L2_PANEL_BUDGET` | 256 KiB | unchanged | S3/S5; enlarging is neutral to worse |
| `PACKED_LINES_BUDGET` | 32 KiB | unchanged | S3 `column_step` flat across the capped range |
| `TASKS_PER_THREAD` | 4 | unchanged | 91% scaling efficiency on `Aᵀ*X` |
| `TASK_AXIS_FLOOR` | 256 | unchanged | S2/S3 optimum sits at 256 |

The docstrings can drop "heuristic default awaiting one benchmark run on an
AVX2/AVX-512 x86 machine" and cite this file instead. No constant changes
value.

## Open items

- `A*x` thread scaling at 40% efficiency, with a non-monotonic point at 4
  threads, is undiagnosed.
- The `k = 1` vector kernels still allocate 12.8 KB and 21.2 KB per call in
  `Threads.@spawn` task objects, which is now the whole allocation figure
  for them.
- `A*X` tops out at 256 GFMA/s (`Float32`, k = 128) against 626 GFMA/s for
  `Aᵀ*X`. The forward register tile is the slower of the two directions and
  the narrowest margin over upstream; unlike the transpose kernel it gains
  nothing from the rhs width choice, so the cost is elsewhere — most likely
  the per-row `values[_packed_code(...)]` lookup in `_multiply_add_rows`.
- Measured on 12 cores of one socket only. A 36- or 72-core point, and the
  memory-bound regime past L3 (R = 100, ~512 MB packed), were not run.
